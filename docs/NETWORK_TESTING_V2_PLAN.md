# План разработки Network Tester v2

## Цель

Сделать результаты проверки ZUI объяснимыми и устойчивыми к ложным успехам: отделять неисправность сети от проблемы пресета, определять этап отказа, проверять реальные сценарии Discord/YouTube и сохранять корректный итог больших пакетных тестов.

В объём входят согласованные пункты: 1, 2, 3, 4, 5, 7, 8, 9, 10, 11, 12 и 13. Пункт 6 (серии повторов и статистика нескольких попыток) в этот план не включён.

## Общие правила реализации

- Новый движок вводится с версионированными моделями результатов и обратным чтением старой истории.
- Сетевой результат имеет состояния `passed`, `failed`, `inconclusive`, `cancelled`; `inconclusive` не ухудшает рейтинг.
- Ошибка всегда содержит этап: `process`, `dns`, `tcp`, `tls`, `http`, `content`, `websocket`, `quic`, `udp` или `resource`.
- Baseline не смешивается с результатом пресета: UI показывает изменение `до -> после`.
- Тесты ограничивают время, размер ответа и число параллельных операций; отмена должна останавливать незавершённые операции.
- Стандартные цели и правила находятся в одном Rust-манифесте. Svelte получает их через Tauri API.
- Каждый этап заканчивается работающей сборкой, миграцией данных, тестами и ручным контрольным прогоном.

## Этап 1. Фундамент тестового движка и достоверная классификация

Покрывает пункты 1, 2, 3, 7, 8 и 11.

### 1.1. Новая модель данных

Создать отдельный модуль тестирования вместо дальнейшего разрастания `tester.rs`:

- `tester/model.rs` — версии моделей, статусы и типы ошибок;
- `tester/manifest.rs` — описание сервисов и целей;
- `tester/baseline.rs` — исходный снимок сети;
- `tester/probes/` — интерфейс сетевых проб;
- `tester/scoring.rs` — правила рейтинга;
- `tester/runner.rs` — жизненный цикл теста;
- `tester/storage.rs` — сохранение и миграция результатов.

Основные сущности:

- `TestSession` — один быстрый или пакетный запуск;
- `BaselineSnapshot` — состояние сети без Zapret;
- `PresetTestResultV2` — результат одного пресета;
- `ProbeResult` — один этап проверки;
- `ProbeStatus` — passed/failed/inconclusive/cancelled;
- `FailureStage` и нормализованный `FailureReason`;
- `ServiceScore` и итоговая рекомендация.

Старые `TestResult` читать через миграцию, не удаляя пользовательскую историю.

### 1.2. Единый манифест целей

Перенести стандартные Discord/YouTube/Google/Cloudflare/DNS цели из `App.svelte` и `tester.rs` в один Rust-манифест.

Для цели хранить:

- идентификатор и сервис;
- тип пробы;
- адрес и порт;
- ожидаемые статусы, заголовки, JSON-поля или признаки содержимого;
- таймаут и максимальный размер ответа;
- вес;
- обязательность (`required`);
- участие в baseline;
- поддерживаемые протоколы.

Добавить Tauri-команду `get_test_target_manifest`. Редактор пользовательских целей должен валидировать значения на backend, а UI только отображать результат валидации.

### 1.3. Baseline до Zapret

Перед тестом гарантированно остановить принадлежащие ZUI процессы Zapret и выполнить компактный набор контрольных проб.

Для одиночного теста baseline выполняется непосредственно перед пресетом. Для пакетного теста:

- полный baseline в начале;
- сетевой fingerprint: активный адаптер, шлюз, DNS-серверы;
- обновление baseline при изменении fingerprint или по истечении ограниченного срока;
- результат конкретного пресета сравнивается только с действующим baseline.

Классификация изменения:

- `unblocked` — до не работало, после работает;
- `unchanged_available` — работало до и после;
- `unchanged_blocked` — не работало до и после;
- `regressed` — работало до, после перестало;
- `inconclusive` — сравнение невозможно.

### 1.4. Настоящий DNS

Добавить отдельные пробы:

- системное разрешение имени;
- DNS A/AAAA через UDP/53;
- fallback TCP/53 для обрезанного ответа;
- контроль идентификатора запроса, имени и типа записи;
- измерение времени ответа;
- отдельные ошибки timeout, malformed response, NXDOMAIN, SERVFAIL и connection failure.

Ping DNS-IP остаётся диагностикой маршрута и не называется DNS-проверкой.

### 1.5. Контроль процесса Zapret

Заменить фиксированное ожидание на проверяемый lifecycle:

- дождаться ожидаемого `winws.exe` или `winws2.exe` с таймаутом;
- проверить, что процесс не завершился в течение grace-периода;
- сохранить PID и engine;
- контролировать процесс между группами сетевых проб;
- при аварийном завершении пометить оставшиеся проверки как inconclusive с причиной `process_exited`;
- останавливать только процессы, запущенные текущим тестом.

### 1.6. Взвешенный рейтинг

Считать итог в два уровня:

1. Оценка сервиса из его обязательных и дополнительных возможностей.
2. Итоговая оценка из явно заданных весов сервисов.

Правила:

- inconclusive и cancelled не считаются провалом;
- ping не влияет на доступность сервиса либо имеет только диагностический вес;
- провал required-проверки ограничивает максимальный статус сервиса;
- regression получает более сильный штраф, чем unchanged_blocked;
- UI показывает вклад каждого сервиса в итог.

### 1.7. UI этапа 1

Показать:

- baseline и результат после пресета;
- точный этап отказа;
- статус процесса;
- DNS-результаты;
- причины inconclusive;
- объяснение итогового рейтинга.

### Критерии готовности этапа 1

- Нет дублирования стандартных целей в Rust и Svelte.
- DNS проверяется DNS-пакетом, а не ping.
- Можно отличить отсутствие интернета от неэффективного пресета.
- Завершившийся `winws/winws2` не порождает ложную оценку сети.
- Старые результаты открываются после обновления.
- `cargo test`, `cargo clippy`, `npm run check` проходят.
- Ручные сценарии проверены: без сети, сломанный DNS, занятый процесс, рабочий и нерабочий пресет, отмена теста.

## Этап 2. Реальные протоколы сервисов и защита от ложных успехов

Покрывает пункты 4, 5, 9 и 10.

### 2.1. Пошаговый HTTPS probe

Для важной цели сохранять отдельные результаты:

1. DNS;
2. TCP connect;
3. TLS handshake с правильным SNI;
4. проверка сертификата и имени;
5. HTTP-запрос;
6. конечный URL после редиректов;
7. ожидаемый статус;
8. заголовки;
9. ограниченный фрагмент содержимого.

Не считать любой статус `< 500` успехом. Разрешённые статусы задаются манифестом. `401`, `403`, `404`, `429`, CAPTCHA и подозрительная страница получают отдельные результаты.

### 2.2. Реальные проверки Discord

Минимальный набор:

- Discord Gateway API: HTTP 200, валидный JSON и поле `url`;
- WebSocket к Gateway: успешный upgrade и получение ожидаемого Hello;
- основной web endpoint с проверкой домена и признаков ответа;
- CDN с контролируемым небольшим объектом;
- отдельная UDP/voice readiness-проба, если её можно выполнить без аккаунта и пользовательских данных.

Gateway/WebSocket является required-проверкой для полного статуса Discord.

### 2.3. Реальные проверки YouTube

Минимальный набор:

- главная страница с проверкой характерного ответа;
- статический ресурс;
- получение небольшого диапазона медиаданных;
- проверка хоста семейства `googlevideo`;
- HTTP/2;
- QUIC/HTTP3 readiness.

Полный статус YouTube требует доступности web и media; одна открывшаяся главная страница недостаточна.

### 2.4. Протокольные пробы

Добавить:

- HTTP/1.1;
- HTTP/2;
- TLS 1.2;
- TLS 1.3;
- WebSocket;
- QUIC/HTTP3;
- ограниченную UDP-пробу.

В результате сохранять фактически согласованные TLS/ALPN/HTTP версии. Неподдерживаемый локальной системой протокол отмечается inconclusive, а не failed.

### 2.5. Защита от кэша и блок-страниц

- уникальный неперсональный nonce на тестовую сессию;
- `Cache-Control: no-cache` там, где это допустимо;
- контроль конечного домена после редиректа;
- ограничение тела ответа, например 64 КиБ;
- сигнатуры известных captive portal и страниц блокировки;
- проверка Content-Type, JSON-полей и обязательных маркеров;
- запрет передачи идентификаторов пользователя, токенов и содержимого профиля.

### 2.6. Собственный ZUI probe endpoint

Создать отдельный минимальный сервер/worker с endpoints для:

- фиксированного JSON;
- редиректа;
- небольшого бинарного файла и Range-запроса;
- WebSocket echo;
- HTTP/1.1 и HTTP/2;
- HTTP/3/QUIC, если выбранная платформа размещения поддерживает;
- диагностического ответа без журналирования пользовательских идентификаторов.

В репозитории должны быть исходники, конфигурация развёртывания, healthcheck и документированная политика данных. Клиент не должен считать доступность собственного endpoint доказательством доступности Discord/YouTube; это только контролируемая протокольная диагностика.

### 2.7. UI этапа 2

Показать матрицу возможностей сервиса:

- Web/API;
- CDN/media;
- WebSocket;
- UDP/voice;
- HTTP/3;
- этап и причина отказа;
- изменение относительно baseline.

### Критерии готовности этапа 2

- Страница блокировки с HTTP 200 не становится успешным результатом.
- HTTP 403/404/429 не считаются доступностью по общему правилу.
- Discord Gateway проверяется реальным WebSocket handshake/Hello.
- YouTube не получает Passed без media-проверки.
- HTTP/3 и UDP не смешиваются с TCP/HTTPS.
- Размер сетевого ответа ограничен и не создаёт заметного роста памяти.
- Собственный endpoint развёртывается воспроизводимо и имеет автоматический healthcheck.

## Этап 3. Пакетные тесты, целостность ресурсов и выпуск

Покрывает пункты 12 и 13 и завершает интеграцию предыдущих этапов.

### 3.1. Новая модель хранения batch-сессии

Разделить данные:

- подробные результаты последних 100 тестов;
- компактная сводка всех пресетов текущей и завершённой batch-сессии;
- лучший результат по каждому пресету;
- top-рекомендации;
- baseline и сетевой fingerprint сессии.

Ограничение 100 применяется только к подробным probe-данным. Сводка на 500 пресетов должна сохраняться полностью. Событие `test_batch_finished` передаёт и сохраняет итоговую сводку, а frontend не очищает её до загрузки сохранённого результата.

### 3.2. Целостность локальных ресурсов

Ввести версионированный resource manifest, создаваемый при сборке:

- относительный путь;
- обязательность;
- размер;
- SHA-256;
- версия комплекта;
- ожидаемая архитектура;
- принадлежность Classic/Zapret 2/общим данным.

Диагностика проверяет:

- наличие всех обязательных файлов;
- размер и SHA-256;
- PE-архитектуру исполняемых файлов;
- версию, если она доступна;
- наличие DLL, WinDivert и списков;
- безопасный self-check исполняемого файла с таймаутом, без запуска фильтрации.

Пользовательские пресеты и изменяемые списки не сравнивать с заводским SHA-256 как повреждённые; показывать их отдельной категорией.

### 3.3. Миграции и устойчивость

- атомарная запись новых session/summary файлов;
- резервная копия повреждённого JSON;
- ограничение размеров импортируемых файлов;
- проверка схемы при импорте;
- восстановление UI после перезапуска во время незавершённого теста;
- гарантированная остановка дочерних процессов при отмене и аварии.

### 3.4. Производительность

Проверить:

- отсутствие накопления probe-ответов в памяти;
- освобождение временных результатов после завершения;
- ограниченную очередь сетевых задач;
- отсутствие лишних WebView-событий для каждого внутреннего этапа;
- пакетный тест 500 пресетов на синтетическом быстром probe backend;
- отмену при DNS, TCP, TLS, WebSocket и QUIC ожидании.

### 3.5. Финальная QA-матрица

Автоматические тесты:

- unit: scoring, manifest, DNS parsing, HTTP validation, migrations, resource manifest;
- integration: локальные DNS/TCP/TLS/HTTP/WS тестовые серверы;
- failure injection: timeout, NXDOMAIN, неверный сертификат, redirect loop, block page, процесс завершился;
- frontend: отображение baseline/delta/inconclusive и сохранённой batch-сводки.

Ручные тесты Windows:

- нормальный интернет;
- отключённая сеть;
- сломанный DNS;
- captive portal или тестовая блок-страница;
- рабочий и нерабочий пресеты Classic/Zapret 2;
- тест всех пресетов;
- отмена на каждом этапе;
- установленная и portable сборки.

### Критерии готовности этапа 3

- Лучший результат не теряется после теста более 100 пресетов.
- После перезапуска доступна полная компактная сводка batch-сессии.
- Повреждённый обязательный ресурс обнаруживается до запуска движка.
- Пользовательские изменяемые файлы не получают ложную ошибку SHA-256.
- Нет зависших процессов после отмены или аварии.
- Потребление памяти остаётся ограниченным на длинном batch-тесте.
- Все проверки и release-сборка проходят; подготовлен changelog с новой семантикой результатов.

## Порядок выполнения внутри каждого этапа

1. Зафиксировать схему и миграцию.
2. Написать unit/integration fixtures для ожидаемого поведения.
3. Реализовать backend.
4. Подключить Tauri API и события.
5. Обновить Svelte UI.
6. Провести автоматические проверки.
7. Выполнить ручные контрольные сценарии.
8. Сохранить отдельный коммит этапа с описанием измеримых изменений.

## Границы релизов

- После этапа 1: внутренний prerelease Network Tester v2 foundation.
- После этапа 2: функциональный prerelease для реального тестирования Discord/YouTube.
- После этапа 3: кандидат на стабильный релиз после длительного пакетного прогона и проверки ресурсов.
