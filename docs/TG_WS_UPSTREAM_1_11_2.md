# Обновление Rust tg-ws до функциональности Flowseal 1.11.2

Дата: 17 октября 2026. Встроенный движок: `2.3.4-zui.4`.
Тестовая сборка ZUI: `2.2.4-network-test.5`, проверена перед выпуском `2.2.4`.

Проверена вся цепочка релизов оригинального проекта после 1.10.2.
Контрольный исходник: [Flowseal/tg-ws-proxy v1.11.2](https://github.com/Flowseal/tg-ws-proxy/tree/v1.11.2), commit `307a384`.
Изменения интерфейса Python/Tk, Linux-обновлятора, Docker и упаковки оригинального приложения к ZUI не применяются.

Это самостоятельная реализация на Rust с эквивалентными механизмами; числовой версии Python-проекта встроенный движок не присваивает.
Предыдущее исправление FakeTLS GREASE сохраняется. Дополнительно исправлено фоновое заполнение CF Proxy pool при балансировке: выбранный базовый домен преобразуется в правильный `kwsDC.domain`, а не используется как готовое имя сервера.

## Маршрутизация

H2 включается только вручную, при включённом CF Proxy, для media DC, с TLS и вне test DC.
CLI: `--h2`; `--no-h2` явно отключает режим. H2 по умолчанию выключен в тестовой сборке.

Для медиа сначала проверяется H2. Если он недоступен, применяется существующая лестница WS/CF Worker/CF Proxy/upstream/TCP с учётом CF priority и настроенных прямых DC. Установка H2 ограничена восемью секундами на всю попытку выбора домена, а не на каждый домен по очереди. После timeout действует пауза для этого DC; после ошибки — пауза для домена.

При сетевой ошибке уже работающего H2-канала текущий native-канал закрывается. Telegram переподключается; cooldown позволяет следующему соединению выбрать WebSocket. Прозрачно переносить уже переданные байты между транспортами нельзя.

Переключатель прямых DC управляет WebSocket DC→IP. Резервный raw TCP fallback остаётся отдельным последним маршрутом, как в оригинальном проекте.

## Ограничения и отличия реализации

- Native-пакет: до 4 МиБ; abridged, intermediate, padded intermediate; plain padding до 256 байт.
- До 16 одновременно активных native H2-каналов; остальные соединения используют обычные маршруты.
- До 16 кэшированных lane. Неиспользуемые lane вытесняются при заполнении кэша.
- Канал: до 8 запросов, включая до 2 recovery; 6 мест оставлены оригинальным запросам.
- Пакеты клиента: бюджет 8 МиБ на канал. Ответы: отдельный бюджет 8 МиБ на канал.
- Lane: верхний лимит 64 HTTP streams и 32 МиБ запросов/32 МиБ ответов.
- Память под потенциальный ответ 4 МиБ резервируется до открытия stream. Поэтому одновременно читаемых ответов на lane будет не более восьми, независимо от лимита streams. Это предотвращает взаимную блокировку flow control при нехватке памяти.
- Оригинальные запросы lane дополнительно ограничены шестью одновременными попытками, чтобы recovery имел свободную ёмкость. Это сознательный способ предотвращения перегрузки вместо Python-механизма отмены старых запросов ради освобождения места.
- Общий бюджет native request/reply-очередей: 128 МиБ, разделён на 64 МиБ входящих и 64 МиБ ответов. Это предел учтённых packet-буферов, а не обещание максимальной RAM всего процесса: TLS, HTTP/2, сокеты, интерфейс и allocator имеют собственные расходы.
- Replay history: до 16 небольших зашифрованных пакетов, суммарно до 64 КиБ, срок до 30 секунд. Незашифрованные auth-запросы не повторяются.
- Максимум 3 повтора без нового ответа. Новый идентификатор ответа обновляет бюджет; дубли не доставляются повторно.
- Проверка recovery каждые 250 мс: зависший оригинал от 3 секунд, повтор от 2 секунд, idle polling последнего пакета от 1 секунды. Во время приёма тела или передачи ответа native-клиенту повторы подавлены.
- При ошибке/отмене задачи её permits освобождаются через RAII. При остановке закрываются native-задачи, refill и connection drivers.

## Проверки

Автоматически проверяются framing и padding, фрагментированный шифрованный TCP/FakeTLS обмен, plaintext CF через HTTP CONNECT, миграция старых профилей, пустые DC, backoff, отмена refill, мультиплексирование, HTTP и MTProto transport errors, чрезмерные ответы, deadline, replay/deduplication и освобождение бюджетов.

Нагрузочная регрессия: 1000 последовательных запросов и 100 параллельных ответов по 1 МиБ на одном lane. Отдельный длительный стенд передаёт пять серий по 100 пакетов по 1 МиБ и снимает working set/private bytes процесса.

```powershell
cargo test --manifest-path crates/tg-ws-proxy-rs/Cargo.toml --offline
cargo clippy --manifest-path crates/tg-ws-proxy-rs/Cargo.toml --all-targets --offline -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib --offline
cargo clippy --manifest-path src-tauri/Cargo.toml --lib --offline -- -D warnings
npm run check
npm run build
powershell -NoProfile -ExecutionPolicy Bypass -File tools/measure-tg-ws-h2.ps1
```

Артефакты замера: `.local-build-artifacts/tg-ws-h2/memory-samples.csv` и `memory-summary.json`.
Стенд размещает генератор нагрузки и mock H2-сервер в том же процессе. Его RAM нельзя выдавать за RAM самого ZUI или сравнивать напрямую с WebView2.

Результат замера 17 октября: baseline private bytes 1,91 МиБ; пик нагрузки 103,61 МиБ; после серий в паузах 2,74–3,65 МиБ; после закрытия 2,77 МиБ. Пик working set 111,97 МиБ. Повторяющийся рост после завершения серий не обнаружен в этом коротком стендовом прогоне; это не заменяет длительную проверку в Telegram Desktop.

Дополнительно выполнена реальная проверка стандартного CF-домена: доверенный TLS, ALPN h2, HEAD /api и MTProto `req_pq_multi → resPQ` с проверкой nonce. Она не требует аккаунта или secret пользователя и не заменяет проверку реальной загрузки Telegram media.

```powershell
cargo test --manifest-path crates/tg-ws-proxy-rs/Cargo.toml --lib --offline live_cloudflare_h2_preflight -- --ignored --nocapture
```

Описание протокола: [Telegram MTProto](https://core.telegram.org/mtproto/description), [DH exchange initiation](https://core.telegram.org/mtproto/auth_key).
